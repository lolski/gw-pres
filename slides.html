Null-safety: TypeQL


match
  $u isa user, has name $n;
  try { $u has address $a; };   # $a bound if present, absent otherwise
  

define
fun shipping_address($u: user) -> address?:   # optional in the signature
  match $u has address $a;
  return first $a;

Optionality declared in the schema (@card(0..3)), handled explicitly with try, typed in function signatures.

Null-safety: Cypher


MATCH (u:User) RETURN u.address        // missing → silently null

MATCH (u:User) WHERE u.address = "..."     // null: row dropped
MATCH (u:User) WHERE NOT u.address = "..." // null: ALSO dropped

Null propagates through three-valued logic — bugs no tool warns you about.

The benefit

Cypher

Absence is a sentinel value that leaks through results and blows up in app code.

TypeQL

Absence is a type-level concept, checked by the query compiler.

Cardinality: TypeQL


define
  entity user,
    owns email @key,
    owns name @card(1..1),
    owns address @card(0..3),
    plays transaction:buyer;

  entity good, owns price @card(1..1), plays transaction:item;

  relation transaction,
    relates buyer @card(1..1),
    relates item @card(1..),
    owns amount, owns payment-method, owns date;

Cardinality: Cypher


CREATE CONSTRAINT user_email FOR (u:User) REQUIRE u.email IS UNIQUE;
CREATE CONSTRAINT user_name  FOR (u:User) REQUIRE u.name IS NOT NULL;

// addresses "at most 3"?           — not expressible
// transaction has exactly 1 buyer? — not expressible

Property uniqueness/existence only. No cardinality constraints on relationships at all.

Inheritance: TypeQL


define
  entity good @abstract, owns price @card(1..1), plays transaction:item;
  entity book sub good, owns isbn;
  entity electronics sub good, owns warranty-months;
  

match
  $t isa transaction (buyer: $u, item: $g);
  $g has price $p;    # matches books AND electronics — polymorphic

Inheritance: Cypher


CREATE (b:Good:Book {price: 12.99, isbn: "978-..."})  // multi-label = hope

MATCH (t:Transaction)-[:CONTAINS]->(g:Good)
RETURN g   // works only if everyone remembered the :Good label
  • Nothing stops CREATE (b:Book {...}) without :Good — invisible to every "all goods" query
  • Nothing stops a :Good:User
  • No abstract types: a bare :Good can exist
  • No inherited constraints: price IS NOT NULL re-declared per label

Extract the complicated query


define
fun total_spend($u: user) -> double:
  match
    $t isa transaction (buyer: $u);
    $t has amount $a;
  return sum($a);
  

match
  $u isa user, has name $n;
  let $s = total_spend($u);
  $s > 1000;    # big spenders, one line
