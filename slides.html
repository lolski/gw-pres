Null-safety: TypeQL


match
  $u isa user, has name $n;
  try { $u has address $a; };   # $a bound if present, absent otherwise
  

define
fun shipping_address($u: user) -> address?:   # optional in the signature
  match $u has address $a;
  return first $a;

Optionality declared in the schema (@card(0..3)), handled explicitly with try, typed in function signatures.

Null-safety: Cypher


MATCH (u:User) RETURN u.address        // missing → silently null

MATCH (u:User) WHERE u.address = "..."     // null: row dropped
MATCH (u:User) WHERE NOT u.address = "..." // null: ALSO dropped

Null propagates through three-valued logic — bugs no tool warns you about.

The benefit

Cypher

Absence is a sentinel value that leaks through results and blows up in app code.

TypeQL

Absence is a type-level concept, checked by the query compiler.

Cardinality: TypeQL vs Cypher

TypeQL


define
  entity user,
    owns email @key,
    owns name @card(1..1),
    owns address @card(0..3),
    plays transaction:buyer;

  entity good,
    owns price @card(1..1),
    plays transaction:item;

  relation transaction,
    relates buyer @card(1..1),
    relates item @card(1..),
    owns amount, owns payment-method, owns date;

Cypher


CREATE CONSTRAINT user_email FOR (u:User)
  REQUIRE u.email IS UNIQUE;
CREATE CONSTRAINT user_name  FOR (u:User)
  REQUIRE u.name IS NOT NULL;

// addresses "at most 3"?
//          — not expressible
// transaction has exactly 1 buyer?
//          — not expressible
// transaction has ≥1 good?
//          — not expressible
Property uniqueness/existence only. No cardinality constraints on relationships at all.

Inheritance: TypeQL vs Cypher

TypeQL


define
  entity good @abstract,
    owns price @card(1..1),
    plays transaction:item;
  entity book sub good, owns isbn;
  entity electronics sub good,
    owns warranty-months;
      

match
  $t isa transaction (buyer: $u, item: $g);
  $g has price $p;
  # matches books AND electronics

Cypher


CREATE (b:Good:Book
  {price: 12.99, isbn: "978-..."})
// multi-label = hope

MATCH (t:Transaction)
  -[:CONTAINS]->(g:Good)
RETURN g
// works only if everyone
// remembered the :Good label
No abstract types, nothing stops a bare :Good or a :Good:User, constraints re-declared per label.

All transactions for a user


define
fun transactions_by_user_email($email: string) -> { transaction }:
  match
    $u isa user, has email $email;
    $t isa transaction (buyer: $u);
  return { $t };

The whole query — user lookup included — becomes a single function call:


match
  let $t in transactions_by_user_email("ganesh@typedb.com");
fetch { "transaction": { $t.* } };

The backend collapses


@app.get("/users/{email}/transactions")
def list_transactions(email: str):
    with driver.transaction("shop", TransactionType.READ) as tx:
        query = f'''
            match let $t in transactions_by_user_email("{email}");
            fetch {{ "transaction": {{ $t.* }} }};'''
        return [row for row in tx.query(query).resolve()]

The match is the function call — domain logic lives in the schema, not the service.
